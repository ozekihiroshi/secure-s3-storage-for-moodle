# Secure S3 Storage 0.6.1

This documentation-focused alpha release candidate records the completed AWS
validation of the recovery features introduced through version 0.6.0. Runtime
behavior is unchanged from version 0.6.0.

The plugin was deployed to Moodle 5.2.2 on EC2 as an immutable ZIP-installed
plugin and used the AWS SDK default credential provider chain with an EC2
instance role. No long-lived AWS access key was stored in Moodle. The built-in
database producer created and transferred a verified DTL recovery artifact, and
the matched content task transferred the referenced Moodle `filedir` objects
and published the recovery-set metadata.

The downloaded database and content recovery set passed an isolated rehearsal:
the database was restored into a fresh non-live database, the content inventory
was restored into an empty non-live `filedir`, and a restored object was read
through the Moodle File API. The same gate first proved that a deliberately
checksum-corrupt content inventory is rejected.

The documented retention baseline uses S3 Versioning and prefix-scoped
Lifecycle rules. Course archives, database recovery artifacts, and content
recovery-set metadata expire after 30 days. Shared content objects below the
deduplicated object prefix have no automatic expiration, because one object may
be referenced by multiple recovery sets. Incomplete multipart uploads below the
dedicated plugin prefix are aborted after seven days. Operators must review
storage growth and must not add automatic deletion for shared objects without a
separate reachability-aware garbage-collection design.

The clean-ZIP release gate installs the self-contained plugin into an empty
Moodle 5.2.2 environment. It verifies course backup transfer and restore,
external and built-in database backup transfer, database-matched content
transfer, malformed-manifest and corrupt-payload rejection, isolated database
and `filedir` restoration, and Moodle File API access to restored content.
Moodle Plugin CI separately verifies the supported PHP and database endpoints.

This remains an alpha release for controlled evaluation. Database and content
transfers remain disabled by default. Restore remains CLI-only and must target
an isolated empty database and content directory. Production use requires a
working Moodle Cron, least-privilege runtime IAM credentials, a dedicated S3
prefix, storage and cost monitoring, and regularly rehearsed recovery.
